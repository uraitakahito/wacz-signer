## 仕様書に書かれていない 2 点

どちらも仕様を読んで分かったのではなく、リファレンス実装の出力を分解して分かったことです。そしてどちらを間違えても、**何も検証していないのに完全にそれらしく見えるもの**ができあがります。

### 1. 署名対象は接頭辞込みのハッシュ文字列

署名されるバイト列は `sha256:fcf066f7…` です。hex だけではなく、末尾に改行もありません。hex だけに署名すると openssl は `digest_verify_final` で落ちます。改行を足すと（`echo` は足しますし、多くのエディタは保存時に足します）ダイジェストが変わり、何に対しても検証できない署名になります。

だから wacz-signer は、「何も足さない」ことだけを約束する関数を経由してこのバイト列を書きます。

> 署名はまさにこのバイト列に対して計算される。`echo` が足すような、そして多くのエディタが保存時に足すような `\n` が 1 個紛れ込むだけでダイジェストが変わり、何に対しても検証できない署名ができる。

### 2. `timeSignature` には TimeStampResp 全体が入る

タイムスタンプが覆うのは署名の**バイト列ではなく base64 文字列**です。そして格納されるのは `TimeStampResp` 全体 —— ステータスの包みごと —— であって、その中の裸のトークンではありません。

後者は逆に思い込みやすいので、少し丁寧に書きます。RFC 3161 には要求（`TSQ`）と応答（`TSR`）があり、応答はトークン（`TST`）を**含みます**。`timeSignature` という名前からはトークンが入っていそうに見えます。入っていません。

トークンとして読もうとすると `-token_in` を付けることになり、失敗はこう見えます。

```
asn1_check_tlen:wrong tag … Field=type, Type=PKCS7
```

これは「フラグを間違えた」と伝える言い方としては分かりにくいものです。決着をつけるには、応答として読めるかどうかを openssl に訊きます。

```console
$ openssl ts -reply -in ts.tst -text
Status info:
Status: Granted.
…
Time stamp: Aug  1 13:59:39 2026 GMT
```

読めます。したがって署名側にも検証側にも `-token_in` は要りません。

## 署名する機械とキャプチャする機械を分ける

```console
$ wacz-signer serve --dir ./id --port 8080 --token "$WACZ_SIGNER_TOKEN"
```

`POST /sign` は `{"hash": "sha256:…"}` を受け取り `signedData` を返します。`POST /verify` は `signedData` でも `datapackage-digest.json` 全体でも受け取り、4 段階の報告を返します。

守るのは `/sign` だけで、これは authsign と同じです。キャプチャ側はハッシュを送って署名を受け取るだけで、2 本目のアーカイブに署名できるものは何も持ちません。検証は、そのアーカイブを持っている人が既に知っていること以上を明かさないので開いたままにします。

`/verify` は、通らなかったアーカイブに対しても 4xx ではなく **200 と `valid: false`** を返します。問いには答えられたからです。ここで転送レベルのエラーコードを返すと、サーバが落ちている場合と区別がつかなくなります。それはアーカイブが検証に通らないこととは全く別の事態です。

`serve` は SIGTERM と SIGINT で止まります。受け付けを閉じ、処理中の署名を終えてから（開いたままの keep-alive の接続は切って）終了コード 0 で終わるので、コンテナの停止や配備の入れ替えで待たされません。閉じ切れないときは数秒で諦めて終了コード 1 で終わります。これが無いと、PID 1 の node は信号を無視し、猶予が尽きてから殺されます。
